# Extensions Directory

This directory will contain community-contributed Envoy extensions.

## Structure

Each extension should be in its own directory with:

```
extension-name/
├── README.md            # Description and usage
├── manifest.yaml        # Metadata (name, version, author, etc.)
├── {go,lua,rs}          # Extension code (language-specific)
└── config.schema.json   # (Optional) JSON schema describing the extension configuration
```

## Extension e2e tests

Extension e2e tests live in the [tests/e2e](./tests/e2e) directory. Take a look at the README file
there for details on writing end-to-end tests for your extension.

## Executable manifest examples

Manifest examples can keep a hand-written `code` snippet, or define `config` and `commands` so
the snippet is generated by running the extension. Use a `config` object for executable examples;
`{}` is valid when no settings are needed. Commands are argument arrays and run directly without
a shell. They run in order, and `expectedExit` defaults to `0`. An HTTP denial response does not
make `curl` fail unless the command uses a flag such as `--fail-with-body`.

Use optional `preStart` commands to download or create files that BOE needs at startup. They use
the same command fields and run sequentially before BOE, after fixture staging. Both phases share
the isolated working directory; files created by `preStart` are available to the configuration
and later commands. Any unexpected command failure aborts generation without updating manifests.
Pre-start commands must finish, so they cannot launch a persistent companion service.

Commands may opt into bounded HTTP-status retries with `retry: {httpStatus: 200, maxAttempts: 10}`.
`httpStatus` must be 200–599 and `maxAttempts` 1–10000. A valid response with another status is
retried using the same arguments and working directory, within the command's total timeout. A
non-expected exit, timeout, cancellation, or response that cannot be parsed fails immediately;
retry exhaustion also fails generation. Only the attempt with the requested status is captured.
Generated code adds a comment such as `# Repeat until HTTP 200, up to 10 attempts.` before the
command, but the copied command itself runs once. This helps capture an expected response; it does
not prove that randomized behavior is repeatable. For a probabilistic 200/503 sampler, capture each status in a separate command. This checks
that both cases occur within the bound, not that they occur at the configured rate.

Retries require a direct `curl` command with `--disable` (or `-q`) first and one HTTP(S) URL. Use `--verbose`, `--include`, or a
`--write-out` template starting with `HTTP/%{http_version} %{http_code}` and a newline, followed by
header lines and a blank line. Write-out retries also require `--output /dev/null` to divert the
body. Only the declared capture streams select a status. Redirects, curl-owned retries, multiple
transfers, config files, and unsupported curl options are rejected before execution. URL globbing
requires `--globoff`; HTTPS include capture requires `--suppress-connect-headers`.

An optional `comment` on a command adds display-only `#` lines above it in the generated example.
Comments are not run or placeholder-expanded; edits to their text appear as literal transcript
changes. For the displayed BOE command, `{}` and a single top-level scalar setting use compact
JSON. Configurations with multiple keys or any nested object or array use pretty-printed, indented
JSON.

The generator expands `${PROXY_URL}`, `${ADMIN_URL}`, `${UPSTREAM_ADDRESS}`, and `${WORK_DIR}` in
arguments and configuration strings. It copies the extension's `examples/` fixtures into a
temporary work directory before starting Envoy; use paths relative to that fixture directory in
commands. The default upstream is `httpbin.org:443`, so examples that call it need network access.
Envoy defaults to `1.38.0`; downloads are cached in the ignored
`extensions/out/example-envoy-cache/` directory.

The displayed pre-start commands run from the repository root, before the BOE invocation in
Terminal 1. Their `${WORK_DIR}` paths match the configuration's repository-relative paths.
Request commands run in Terminal 2 after Envoy is ready and use `.` for `${WORK_DIR}` after an
optional `cd` into the fixture directory. Commands wrap at argument boundaries to fit 80 characters
where possible, preserving quoted values and multiline JSON.

Generated `code` contains separate fenced `sh` command blocks and `text` output blocks. This keeps
the commands runnable and shows captured HTTP output as it appeared, including curl's `>` request
and `<` response lines. Use curl's `--verbose` and a stable `--user-agent boe-example` when the
protocol exchange is part of the example. The generator omits curl's `* ` transport
diagnostics and `{ [N bytes data]` / `} [N bytes data]` markers, while preserving curl errors and other stderr output.

The generator adds HTML comments after output blocks to identify stdout or stderr and preserve
line ending types, bare carriage return positions, trailing whitespace, and whether the output ends
in a newline. These comments are part of the compared manifest snippet and are hidden by the website renderer.
Displayed output uses LF line endings, escapes bare CR bytes, and omits trailing spaces and tabs;
metadata keeps those distinctions significant during `check-examples`.
The renderer treats generated code as separate highlighted, copyable
blocks. Legacy examples that contain plain shell text continue to render as one shell block.

For example, an extension that returns a varying latency header can declare:

```yaml
examples:
  - title: Inspect the response
    description: Show the HTTP exchange and response body.
    config: {}
    commands:
      - comment: Show the HTTP exchange and response body.
        argv: [curl, --disable, --silent, --show-error, --verbose, --user-agent, boe-example, --max-time, "10", "${PROXY_URL}/status/200"]
        retry:
          httpStatus: 200
          maxAttempts: 10
    volatileHeaders:
      - x-fault-inserted-latency
```

These fields belong to an entry in `examples`, alongside `title` and `description`. Leave out
`code` for a new executable example; `update-examples` fills it in. HTTP `Date` headers are
handled automatically. Declare other changing response headers by name in `volatileHeaders`;
date or duration format is inferred. Bare duration numbers and values with units are supported.
Only values with the same recognized type and format compare as volatile; unrecognized values
compare exactly. Use response-only `comparison` rules with `type: date` or `duration` and a Go
regexp containing exactly one named `(?P<value>...)` capture for changing values in response text.

For curl verbose output, comparison reads response headers only after a complete initial request
block. It keeps request lines, request headers, status lines, response body, and any unrecognized
format changes byte-for-byte. Only declared response headers and response values matched by
`comparison` rules can vary without failing the check.

Generated code is rewritten only after every selected manifest and command succeeds. The check
mode runs the same examples and compares them without writing files.

Run the tool from the repository root through the extension Makefile entrypoint, setting
`EXTENSION_PATH` to the extension directory:

```sh
make -C extensions update-examples EXTENSION_PATH=example-wasm-go
make -C extensions check EXTENSION_PATH=example-wasm-go
make -C extensions check-examples EXTENSION_PATH=example-wasm-go
make -C extensions test-examples EXTENSION_PATH=example-wasm-go
```

`check` depends on the separate `check-examples` target, which can also be run directly.

Composer is a bundle, so its entrypoint includes the root manifest and every directory in
`PLUGIN_DIRS`, including the built-in `goplugin-loader` manifest:

```sh
make -C extensions update-examples EXTENSION_PATH=composer
make -C extensions check EXTENSION_PATH=composer EXAMPLES_ARGS="-envoy-version 1.38.0"
```

Pass generator options through `EXAMPLES_ARGS`, for example `-boe /path/to/boe`,
`-envoy-version 1.39.0`, `-envoy-path /path/to/envoy`, or `-timeout 2m`.
Use `check-examples` to compare without writing generated snippets.

The generator's [requirements and invariants](../cli/tools/gen-examples/README.md) describe
execution, comparison, and manifest update guarantees.

## Contributing an Extension

1. Fork this repository
2. Create a new directory under `extensions/` with your extension name
3. Add all required files (see structure above)
4. Ensure your README includes:
   - Description of what the extension does
   - Installation/usage instructions
   - Configuration options
   - Examples
5. Open a pull request

## Extension Guidelines

- Extensions should be focused on a single responsibility
- Include comprehensive documentation
- Provide working examples
- Follow Envoy best practices
- Include tests where applicable
